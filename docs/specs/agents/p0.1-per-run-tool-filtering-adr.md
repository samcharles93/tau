# P0.1 ADR: Per-Run Tool Filtering for the Global Registry

**Status**: investigation complete, implementation complete (7/7 design steps done). The `skill` injection contradiction
(G1) has been resolved: `skill` is an ordinary attenuated tool, not a mandatory ambient one. No tool is injected outside
the declared intersection. **Date**: 2026-07-12 **Updated**: 2026-07-13 - resolved skill attenuation contradiction
(CAT-89) **Blocks**: CAT-58 (P2.6 implementation)

## Context

The tool registry is global: `registry.Replace()` / `Unregister()` affect all sessions sharing the same process. Agent
processes running as children need a per-run effective toolset - computed via attenuation (spec tools ∩ parent effective
∩ spawn narrowing) - without mutating global state. Plugin tools may register or unregister mid-flight, and the filter
must never widen beyond the stored effective set.

## Current State

### The `allowedTools` mechanism already exists

`coordinator_turn.go:698` (`buildToolDefs`) is the single interception point where registry schemas are converted to
LLM-visible `ChatToolDef`s. It already applies an `allowedTools` map filter:

```go
// coordinator_turn.go:698-720
func (c *Coordinator) buildToolDefs() []chat.ChatToolDef {
    schemas := c.registry.Schemas()
    c.mu.Lock()
    allowed := c.allowedTools  // nil = unfiltered
    c.mu.Unlock()
    if len(allowed) == 0 {
        filtered = schemas
    } else {
        for _, s := range schemas {
            if allowed[s.Name] { filtered = append(filtered, s) }
        }
    }
    // ...
}
```

Called every turn-loop iteration (line 69-70), so filter changes take effect on the next iteration.

### Current filter limitations

| Limitation                       | Detail                                                                                       |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| Allowlist-only                   | No deny-list or regex; map-based "these tools only"                                          |
| `"skill"` hardcoded              | `SetAllowedTools` always adds `"skill"` to non-empty filters                                 |
| Not persisted                    | In-memory only; lost on coordinator restart                                                  |
| Per-coordinator, not per-session | Single `allowedTools` field shared across all sessions                                       |
| Empty = grant all                | `SetAllowedTools([]string{})` → `nil` → unfiltered (counterintuitive)                        |
| Plugin name collision risk       | Plugin tools use `pluginName__toolName`; a collision with an allowed name would leak through |
| Initial filter via CLI only      | `--tools` / `TAU_TOOLS` sets the constructor-level filter; no config-file equivalent yet     |

### What `spec.Definition.Tools` currently does

- Parsed from YAML frontmatter → `Definition.Tools []string` (`spec.go:46-87`)
- Applied via `SetAllowedTools` when entering agent modes (`coordinator_skills.go:172-173`)
- NOT used in prompt rendering - `RenderAgentPrompt` never passes `def.Tools` (spec body tool lists are for attenuation,
  not prompt injection)
- <code v-pre>{{.Tools}}</code> in `agent.md.tpl` was dead code in production before CAT-82 - `buildAgentSystemPrompt`
  now populates `PromptConfig.Tools` from a temporary registry, so tool name/description pairs render into the system
  prompt

### Plugin tool registration

- `registry.go:242`: `RegisterPluginTool` sanitizes name to `pluginName__toolName`, calls `Replace()` (upsert)
- `registry.go:270`: `UnregisterPluginTools` removes by prefix
- Registry is `sync.RWMutex` protected; `Schemas()` RLock concurrent with `Register()` Lock is safe
- If `allowedTools` is non-nil, newly registered plugin tools are automatically excluded (not in the allowlist)

## Decision

### Chosen mechanism: `allowedTools` field on Coordinator with static initialisation

The existing `allowedTools map[string]bool` on the Coordinator struct is the correct mechanism. It will be extended as
follows:

1. **Make it constructor-initialised, not just runtime-set**. Add `AllowedTools []string` to `CoordinatorConfig`. The
   constructor sets `c.allowedTools` from this value. ✅ _Done - `--tools` CLI flag and `TAU_TOOLS` env var wired
   through `ChatOptions.AllowedTools` → `CoordinatorConfig.AllowedTools` → `Coordinator.allowedTools`._

2. **Store the "ceiling" separately from the "active" filter**. Add a `effectiveTools map[string]bool` that is the
   attenuation-computed ceiling - this is the set the coordinator was born with. The `allowedTools` field becomes the
   _active_ filter (which modes may further restrict by intersecting with `effectiveTools`). A mode can never widen
   beyond `effectiveTools`, and `effectiveTools` is immutable after construction. ✅ _Done - `effectiveTools` is set at
   construction; `allowedTools` starts nil; mode exit reverts to ceiling via `SetAllowedTools([]string{})`._

   ```go
   type Coordinator struct {
       // effectiveTools is the attenuation-computed ceiling, immutable after NewCoordinator.
       // nil means "unrestricted" (root process with no spec tool list).
       effectiveTools map[string]bool
       // allowedTools is the active filter (effectiveTools ∩ mode restriction).
       // nil means "no active restriction beyond effectiveTools".
       allowedTools map[string]bool
   }
   ```

3. **Change `SetAllowedTools` to intersect with `effectiveTools`**: ✅ _Done - empty list reverts `allowedTools` to nil
   (ceiling-only); non-empty intersects with `effectiveTools`._

   ```go
   func (c *Coordinator) SetAllowedTools(toolNames []string) {
       if len(toolNames) == 0 {
           c.allowedTools = c.effectiveTools  // revert to ceiling
           return
       }
       m := make(map[string]bool, len(toolNames)+1)
       m["skill"] = true
       for _, name := range toolNames {
           if c.effectiveTools == nil || c.effectiveTools[name] {
               m[name] = true
           }
       }
       c.allowedTools = m
   }
   ```

4. **`buildToolDefs` applies BOTH filters**: ✅ _Done - two-tier check: effectiveTools ceiling first, then allowedTools
   active filter._

   ```go
   func (c *Coordinator) buildToolDefs() []chat.ChatToolDef {
       schemas := c.registry.Schemas()
       c.mu.Lock()
       effective := c.effectiveTools
       allowed := c.allowedTools
       c.mu.Unlock()

       for _, s := range schemas {
           if effective != nil && !effective[s.Name] { continue }
           if allowed != nil && !allowed[s.Name] { continue }
           filtered = append(filtered, s)
       }
   }
   ```

5. **Nil semantics**: `effectiveTools == nil` means "unrestricted" (the root process or an agent without a `tools:`
   list). `allowedTools == nil` means "no mode restriction active". Both must be nil to pass all tools.

6. **Plugin mid-flight rule**: The `effectiveTools` ceiling is immutable. Plugin tools registered mid-flight are checked
   against it in `buildToolDefs`. If the plugin tool's name is not in `effectiveTools` (and `effectiveTools` is
   non-nil), it is invisible to the LLM. This is "never widen" - exactly what we want.

7. **`spec.Definition.Tools` semantics doc**: `nil` = no restriction from the spec. `[]` (empty list) = unknown; treat
   as nil for now. `["read", "grep"]` = only these tools. The `agent` tool participates: omitting it from the list
   disables spawning from that agent.

### Rejected alternatives

| Alternative                                                        | Why rejected                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Filter in the registry itself** (add `FilteredView` to Registry) | Registry is shared; per-run views belong at the consumer level. A registry-level filter would mean every caller must manage its own view, which is equivalent but spreads logic into `registry.go` instead of keeping it local to the coordinator.                                                                                                                                                                                                                                                                                |
| **Deny-list instead of allowlist**                                 | Attenuation requires intersection, which is an allowlist operation. A deny-list could express "everything except X" but not "only these specific tools", and the latter is what specs declare.                                                                                                                                                                                                                                                                                                                                    |
| **Per-session allowedTools**                                       | Tools are a coordinator-level property (the process's capability, not the session's). Moving it to session state would break the "process identity" model (decision 2).                                                                                                                                                                                                                                                                                                                                                           |
| **Make `allowedTools` a `[]string` everywhere**                    | Map lookups in `buildToolDefs` (called every turn iteration) are cheaper than slice scans. The string→bool map is the right representation for the hot path.                                                                                                                                                                                                                                                                                                                                                                      |
| **Remove the `"skill"` hardcode**                                  | ~~The skill tool is how modes are entered and exited; without it, a restricted agent can never switch modes. It stays as a mandatory tool in all non-empty filters.~~ **OVERTURNED (2026-07-13, CAT-89).** `skill` is now an ordinary attenuated tool - it participates in the intersection like any other tool. To enable mode switching, include `"skill"` in the spec's tools list. Omitting it disables mode switching for the agent (user slash-commands still work). No tool is injected outside the declared intersection. |

### edge cases

| Case                                  | Behaviour                                                                                              |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Root process (no spec, no tools list) | `effectiveTools = nil` → full registry available                                                       |
| Child with `tools: [read, grep]`      | `effectiveTools = {read, grep}` after construction (no auto-injected `skill`)                          |
| Child with no `tools:` field          | `effectiveTools = nil` → inherits parent effective (attenuation still applies at the parent level)     |
| Plugin registers a new tool mid-run   | Checked against `effectiveTools` ceiling in next `buildToolDefs` iteration; excluded if not in ceiling |
| Mode further restricts (e.g. `/plan`) | `SetAllowedTools` intersects mode tools with `effectiveTools` ceiling                                  |
| Agent tool removed from ceiling       | Child cannot spawn grandchildren; `agent` tool is invisible to LLM, will never be called               |
