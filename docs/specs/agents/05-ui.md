# UI: Rendering Child Agents

Design constraints, both standing tau principles: state-not-log (the tui2 north star), and TUI/WebUI must not drift. Both surfaces therefore render from the same data: the child's full event stream, forwarded by the parent through the bridge in agent-scoped envelopes. The UI chooses how much to *show*; nothing is withheld from it.

## Event flow

```
child coordinator ── ChatEvents ──> child stdio ── agent.event ──> parent
parent re-publishes onto its bus, scoped to the spawning tool call
   ├──> TUI renders state block / drill-down
   └──> server bridge ── WebSocket ──> WebUI renders the same
```

The parent tags each re-published event with the child's instance address and the spawning tool-call id. The bridge forwards them inside the agent-scoped wrapper (see 03, `agent.event`), so browser clients receive exactly what the TUI receives.

## The state block

While a child runs, the spawning tool call renders as a compact live element, one per child, stacked when a turn fans out:

```
▶ agent research#k3v9qp   reading internal/store/sqlite_store.go   turn 4 · 12.3k · 8s
▶ agent research#m2xw01   grepping "parent_session_id"             turn 2 ·  4.1k · 8s
```

Contents, all derived from the forwarded events and usage messages:

- Agent name and instance id, tinted with the spec's `color` when set
- Current activity: latest tool execution (verb + primary argument) or "thinking" with the tui2 shimmer treatment while a provider call streams
- Turn count and running token/cost figures (from `agent.usage`)
- Elapsed time

Terminal states collapse the block to a single summary line (status, turns, tokens, duration) above the tool result. Abnormal ends colour the status and keep the line visible.

## Drill-down

One keypress (TUI) or click (WebUI) on a state block expands the child's transcript, rendered with the same message components as a normal session view, fed from the forwarded events already held in memory. The durable record is the child's session in the store: from the expanded view the user can open the child session proper (which also survives restarts; live drill-down memory does not need to).

## Session tree

The sessions list gains lineage awareness:

- Child sessions display under their parent (indent or tree glyphs), using `parent_session_id` / `ListChildren`.
- Each row shows the agent identity that ran it (`agent_instance_id` joined to the instance row), so a session is always attributable to a spec + instance.
- Resuming a child session from the list is the manual counterpart of the `resume` spawn parameter.

## Cancellation affordance

While children run, cancel (Esc in the TUI, stop button in the WebUI) targets the parent turn, which propagates `agent.cancel` down the tree (see 02). Cancelling a single child from its state block is a v1-optional nicety; if cheap it sends a targeted `agent.cancel`, otherwise it can wait.

## Non-goals in v1

- No separate "agents panel" or dashboard; children appear where the work happens, inside the conversation.
- No attach-to-foreign-agent UI (requires the socket transport, deferred).
- No live editing of a running child's parameters.
