# P0.2: Coordinator Scoping Audit for Headless Child Runs

**Status**: investigation complete **Date**: 2026-07-12 **Blocks**: CAT-53 (P2.1 headless child entry point)

## Recommendation

**One-shot mode (`RunStdIn`) is the right base for the headless child entry point.** The coordinator already has the
correct abstractions for headless operation: `InteractiveUI` flag, `NonInteractiveBridge`, event bus isolation, and
independent streamer construction. The gaps are in wiring (resume, parent I/O), control flow (multi-turn), and output
format (structured envelopes) - all additive, not architectural rewrites.

## Blocker Inventory

### Blockers for P2.1 (must resolve before implementation)

| #   | Blocker                                | Detail                                                                                                                                                                                                                          |
| --- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **No session resume in headless path** | `RunStdIn` ignores `opts.ResumeSessionID`. For child runs, the parent creates the instance row and session, then spawns the child with `instance_id` and `session_id`. The child must load its instance, attach to its session. |
| 2   | **No structured output**               | Current `RunStdIn` only prints text deltas to stdout. Child runs need structured envelope output (JSONL) on stdout per the wire protocol (`03-wire-protocol.md`).                                                               |
| 3   | **Single-turn only**                   | Exits after one response. Children may need multi-turn operation (budgets, task completion).                                                                                                                                    |
| 4   | **No parent communication channel**    | No mechanism for parent to send commands (cancel, assign) or receive events (usage, result). stdio pipe protocol in 03-wire-protocol.md defines this.                                                                           |
| 5   | **Single-provider runtime**            | `RunStdIn` uses `newRuntimeForProvider` (fixed). Child needs the resolved provider/model pair injected by the parent, not auto-discovered. Acceptable: the parent resolves and passes the concrete pair.                        |

### Non-blockers (can ship after P2.1)

| #   | Item                                         | Detail                                                                           |
| --- | -------------------------------------------- | -------------------------------------------------------------------------------- |
| 6   | **`persistDefaultsOnUpdate` writes to disk** | Harmless; child won't change provider/model mid-run                              |
| 7   | **Metric collection**                        | `RunStdIn` already has UsageTracker; can forward to parent per P3.3              |
| 8   | **Plugin hot-reload**                        | Already works in headless; `OnReady` just loads immediately instead of deferring |

## Refactor Plan for P2.1

### Phase A: CoordinatorConfig additions (no coordinator changes needed)

Add to `CoordinatorConfig`:

- `InstanceID string` - the agent instance address (e.g. `research#k3v9qp`), used for `from`/`to` in wire envelopes
- `SessionID string` - pre-created session to attach to (child doesn't create its own)
- `ResolvedModel chat.ChatModelRef` - the concrete provider/model pair, already resolved by parent
- `AllowedTools []string` - the attenuated effective toolset (feeds P0.1's constructor-init `effectiveTools`)
- `MaxTurns int` - structural turn cap from spec or config
- `Deadline time.Time` - spawn budget deadline

The coordinator constructor requires zero changes - these are all additive fields with zero defaults.

### Phase B: Child entry CLI

New hidden flag on root command (not shown in help):

```
tau --child         # child mode: reads agent.assign on stdin
```

Implemented as a new function `RunChild(ctx, opts)` in `internal/app/child.go`:

```go
func RunChild(ctx context.Context, opts ChatOptions) error {
    // 1. Write agent.ready to stdout (instance_id, pid, protocol_version)
    // 2. Read agent.assign from stdin (instance_id, session_id, model, tools, depth, budget)
    // 3. Validate instance_id/session_id against store
    // 4. Build coordinator with injected model, tools, limits
    // 5. Start+Load session
    // 6. Read agent.assign.task → SubmitChatPromptCommand
    // 7. Loop: forward ChatEvent as agent.event envelopes on stdout
    //      until ChatResponseCompletedEvent
    // 8. Persist session, write agent.result envelope, exit 0
    // Error paths: write agent.result with status: failed + detail
}
```

### Phase C: Bridge/message types (separate story: CAT-54, P2.2)

Wire envelope types: `agent.ready`, `agent.assign`, `agent.event`, `agent.usage`, `agent.cancel`, `agent.result`.
Defined in `internal/chat/types.go` or a new `internal/agent/wire/` package per 03-wire-protocol.md.

## Confirmation: One-Shot Mode is the Right Base

The existing one-shot path (`RunStdIn` in `internal/app/stdin.go`) demonstrates that the coordinator works headlessly.
The child entry (`RunChild`) is a parallel function, not a modification - it reuses the same `buildCoordinator` and the
same `CoordinatorConfig` with a few extra fields. The two paths share the same coordinator turn machinery (anti-drift
principle, decision 4) by construction.

**The coordinator itself requires ZERO changes for headless child operation.** Every adaptation happens in the
orchestration layer (`internal/app/child.go`) and the coordinator configuration struct.
